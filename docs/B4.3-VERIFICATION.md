## Implementation decisions

- Ranking is organizer-only, scoped by both event and run, using B4.2's run-row
  lock to serialize with submission, closure, and concurrent reranking.
- The existing ScoreRun identical-evidence policy is reused: return the existing
  immutable result and do not emit another audit/outbox event.
- B4.1 solver mathematics and hashing are unchanged. Project IDs come from the
  permanently frozen run snapshots. Comparison IDs/winner/loser pairs are sorted
  and passed to the existing hash utility and solver. The audit stores the exact
  input project/comparison IDs for historical replay.
- Reads use repeatable-read snapshots and compare hashes for current/stale status.
  Names come only from pinned submissions. Historical result rows never change.
- `PAIRWISE_RANKING_CREATED` follows the existing AuditService outbox path, exactly
  like `EVENT_IMPORTED`. Payload schema version is 1. Failure after creating audit,
  outbox, and delivery rows rolls everything back with the ranking and results.
- No schema or migration changes are required. The existing unique key and
  immutable-table triggers remain in force.
- API-FIRST inventory: 102 rows, 108 API paths, 131 operations, zero unmatched UI
  actions and zero stale inventory rows.

## Browser setup

Environment: macOS, Node v24.10.0, existing PostgreSQL Docker container, locally
built API and Next.js web app, Playwright Chromium, one worker. This is not the
B4.4 production Docker cold boot.

Use the existing `.env` credentials with the database name changed to
`dogfood_b43_recovery_test`; never point browser fixtures at the application DB.
Start the API with `WEB_ORIGIN=http://localhost:3103`, `API_PORT=4104`, and
`WEBHOOK_WORKER_DISABLED=true`. Configure the existing required development
webhook encryption key and judge-record signing seed, then run:

```sh
npm run build
node apps/api/dist/main.js
```

In a second terminal:

```sh
API_INTERNAL_URL=http://127.0.0.1:4104 npm exec --workspace @dogfood/web -- next start -p 3103
```

With the same test `DATABASE_URL` exported:

```sh
WEB_URL=http://localhost:3103 npx playwright test tests/browser/pairwise.test.ts --reporter=line
```

The executed API bootstrap directly called `createApp('http://localhost:3103')`
and `app.listen(4104, '127.0.0.1')` from the built `bootstrap.js`, loading `.env`
with `dotenv` and overriding only the test database and worker setting. This
matches the normal `main.js` bootstrap above with explicit environment values.
The browser tests create their own fixture users and log in through the UI.
No arbitrary sleeps are used; actions await responses or observable UI state.

## 30–45 second demo

Prepare an event with three submitted projects, an assigned judge, and a published
Pairwise run. Leave one comparison pending and enough submitted evidence to connect
the projects. Keep organizer and judge sessions in separate browser contexts.

1. **0–8 seconds:** Judge workspace → Open Pairwise Mode. Show the two cards and
   their “Immutable submission snapshot · version 1” labels.
2. **8–15 seconds:** Choose Project A or B → Confirm and submit comparison. Show
   the read-only result and completed count.
3. **15–23 seconds:** Switch to organizer Judging → Pairwise Mode → Refresh pairwise
   progress. Show submitted completion and connected evidence graph.
4. **23–33 seconds:** Click Run Bradley–Terry ranking. Show global ordering and point
   to `BRADLEY_TERRY_RIDGE_V1`, `lambda = 0.01`, and “connected graph”.
5. **33–40 seconds:** Expand ranking diagnostics and show the immutable input hash.
   If a previous ranking exists, select it to show its stale warning.
6. **Optional, up to 45 seconds:** Select a prepared run with disconnected evidence
   and show the explicit global-ranking refusal and component diagnostics.
